# 채점기

채점기(`app/judge`)는 제출 코드를 하위 프로세스로 실행하고 케이스의 출력을 비교한다. 이 문서는 지원 언어, 두 가지 방식, 결과 종류, 시간 제한, 환경 변수 거르기, 격리 여부를 설명한다.

**제출 코드는 격리되지 않는다.** 사용자 권한으로, 사용자 기기에서 실행된다. 자세한 내용은 [격리 없음](#격리-없음)과 [보안](security.md)에 있다.

## 지원 언어와 도구

| 언어 | 필요한 도구 | 특징 |
|---|---|---|
| python | `python3`·`python`(POSIX), `python`·`py`·`python3`(Windows) | 빌드 없음 |
| javascript | `node` | 함수 모드는 `vm` 컨텍스트에서 실행 |
| java | `javac`, `java` | 함수 모드는 `FunctionRunner` 호출 |
| cpp | `g++`, 없으면 `clang++` | C++17, `-O2` |
| rust | `rustc` | edition 2021, `-O` |

- 도구는 있는지만 본다(`shutil.which`). 버전은 확인하지 않는다. 없으면 그 언어는 `toolchain_missing`으로 끝나고 채점하지 않는다.
- Python은 표에 적은 순서로 찾아 처음 있는 것을 쓴다.

빌드와 실행 명령은 다음과 같다. 함수 모드 기준이다.

```text
Java     javac -encoding UTF-8 Solution.java FunctionRunner.java → java -Xss256m <UTF-8 설정> FunctionRunner <번호>
C++      <컴파일러> -std=c++17 -O2 -I. <파일> -o app            → ./app [번호]
Rust     rustc --edition 2021 -O <파일> -o app                  → ./app [번호]
Python   (빌드 없음)                                            → <python> algoblock_runner.py <번호>
JS       (빌드 없음)                                            → node algoblock_runner.js <번호>
```

빌드는 한 번, 실행은 케이스마다 한 번 한다. `<UTF-8 설정>`은 JVM의 표준 입출력을 UTF-8로 맞추는 속성(`file.encoding`, `stdout.encoding`, `stderr.encoding`과 JDK 18의 `sun.stdout.encoding`, `sun.stderr.encoding`)이다. 관으로 이은 표준 출력은 OS 기본 인코딩을 따라서, 이것이 없으면 Windows에서 한글이 깨진다. macOS·Linux에서는 C/POSIX 로케일이 아니면 바뀌지 않는다(그 로케일에서는 깨지던 한글이 바로 나온다). C++는 작업 폴더에 `bits/stdc++.h`를 만들고, macOS에서 링커가 `tapi error`를 내면 설치된 다른 SDK로 다시 링크한다.

## 두 가지 방식

- 함수 모드: `solution`을 부르고, 반환값을 JSON 한 줄로 찍어 비교한다. 케이스의 `input`은 인자 배열을 담은 JSON 글이다.
- 프로그램 모드: 표준 입력을 넣고 표준 출력을 비교한다. 케이스의 `input`은 표준 입력 글이다.

방식은 다음 순서로 정한다.

1. 문제에 저장된 방식이 있으면 그대로 쓴다. 앱 서버가 `mode`로 넘긴다.
2. 없으면 문제 글의 단서를 본다. 함수 단서는 `solution`, '함수를 완성'이다. 프로그램 단서는 '표준 입력/출력', `stdin`, `stdout`, '첫째 줄', '입력 형식', `class Main`, '예제 입력 N' 꼴의 표준 입출력 형식이다.
3. 한쪽 단서만 있으면 그 방식이다.
4. 둘 다 있거나 없으면 코드를 본다. `solution`만 있으면 함수, `main`만 있으면 프로그램이다.
5. 그래도 못 정하면 `undecided`로 끝나고 채점하지 않는다.

고른 방식의 진입점이 없고 다른 방식의 진입점과 케이스가 있으면, 다른 방식으로 한 번 다시 실행한다(`fallback_from`).

함수 모드의 호출 코드는 언어마다 다르다. Java, C++, Rust는 `solution`의 인자 형을 읽어 케이스마다 리터럴로 부르는 코드를 만든다. Python은 맨 위의 `solution`을 부르고, 없으면 `class Solution`의 메서드를 부른다.

- 받는 인자 형은 int, long, double, bool, string과 그 1·2차원 배열이다. 그 밖의 형은 `unsupported_signature`다. 4,000자가 넘는 인자는 파일로 넘긴다.
- C++, Rust의 함수 모드에서는 제출 코드의 `main`을 이름을 바꿔 실행되지 않게 한다.

## 케이스와 결과 종류

- 케이스 모양: `{"id", "input", "expected"[, "timeout"]}`. `timeout`이 있으면 효율성 케이스다.
- 케이스 결과: `passed`, `failed`, `runtime_error`, `timeout`, `output_limit`, `memory_limit`, `skipped`.
- 채점하지 못한 결과: `toolchain_missing`, `undecided`, `entry_missing`, `no_cases`, `unsupported_signature`, `bad_case`, `compile_error`. 컴파일 시간 초과는 `timeout`이다.
- 전체 상태는 `passed`나 `skipped`가 아닌 첫 케이스의 상태다.
- 실행 오류와 컴파일 오류는 사용자 코드의 줄 번호(`line`, `compile_line`)를 알 수 있으면 붙인다.
- 시간 초과가 세 번 이어지면 남은 케이스는 `skipped`로 둔다.

## 출력 비교

함수 모드는 표준 출력의 마지막 줄을 JSON으로 읽어 비교한다. JSON이 아니면 글로 비교한다.

- 정수 기대값은 정확히 같아야 한다.
- 실수로 낸 정수 답(예: 3.0)은 정확히 그 정수이고 절댓값이 2^53 이하일 때만 맞다.
- 실수 기대값은 상대 오차와 절대 오차를 1e-6으로 두고 비교한다.
- bool은 bool끼리만 같다.
- 목록은 길이와 원소를, 객체는 키와 값을 비교한다.
- 기대값이 따옴표 없는 글이면 반환 문자열과 글로 비교한다.

프로그램 모드는 줄마다 끝 공백을 뺀 뒤, 끝의 빈 줄을 뺀 다음 비교한다. `\r\n`은 `\n`과 같다. 앞 공백은 답의 일부다. 소수 비교는 `decimal`이 켜졌을 때(문제에 '실수 답' 표시)만 하고, 그때 기대 출력에 소수로 적힌 낱말을 1e-6 오차 안에서 같게 본다. 기본은 글자 그대로 견준다. 출력은 UTF-8로 읽고 `\r\n`을 `\n`으로 바꾼다.

## 시간과 메모리

- 케이스 하나의 기본 제한은 10초다. 컴파일은 한 번에 60초다. 표준 출력과 표준 오류는 각각 4,000,000바이트를 넘으면 끝낸다(`output_limit`).
- 메모리가 2,048MB를 넘으면 끝낸다(`memory_limit`). 0.25초마다 잰다. POSIX는 `ps -o rss=`, Windows는 작업 집합으로 잰다. 컴파일러는 재지 않는다.
- CPU 시간 상한: 벽시계 제한의 4배에 5초를 더한 값이다. 기본 10초면 45초다. 프로세스마다 걸린다.
  - POSIX: `RLIMIT_CPU`로 exec 전에 건다. 이미 더 낮은 hard 한도가 있으면 그것을 쓴다.
  - Windows: 작업 객체(Job Object)의 프로세스별 사용자 모드 시간 상한(`PerProcessUserTimeLimit`)으로 건다. 커널 모드 시간은 세지 않는다.
- Windows는 작업 객체에 커밋 메모리 상한도 건다. 작업 전체(제출 코드와 그 자식)에 4,096MB(메모리 상한의 2배)다. 넘는 할당은 거절된다. 그래서 프로그램이 실행 오류(`MemoryError`, `bad_alloc` 등)로 끝나면, 작업이 완료 포트로 보낸 '작업 메모리 상한' 알림을 보고 `memory_limit`로 판정한다(POSIX와 같은 이름). Windows는 이 알림의 전달을 보장하지 않으므로, 알림을 받지 못하면 실행 오류로 남는다. 컴파일러에는 이 상한을 걸지 않는다.
- Windows는 작업 안의 동시 프로세스 수에도 상한(`ActiveProcessLimit`)을 건다. 64개다. 정상 풀이는 주 프로세스 하나(venv의 `python.exe`는 둘)이고 `subprocess`·`multiprocessing`으로 몇 개를 더 띄울 수 있어, 보통 기기의 `multiprocessing.Pool`(논리 CPU 수)도 들어가게 넉넉히 잡았다(논리 CPU가 60개를 넘는 기기의 `Pool()`은 막힐 수 있다). 끝없이 프로세스를 만드는 코드는 이 수에서 막혀 더는 만들지 못한다. 막혀서 끝난 실행은 작업의 알림(완료 포트)을 받으면 표준 오류에 `프로세스 수 상한(64)에 걸렸어요` 한 줄이 붙는다. 알림 전달은 보장되지 않는다. 컴파일러에는 걸지 않는다(컴파일러 등이 자식을 많이 띄운다). POSIX에는 이 상한이 없다.
- Windows의 실행 시간(`time_ms`)은 프로세스를 작업에 넣고 재개한 뒤부터 잰다. 작업을 준비하는 시간은 넣지 않는다.

효율성 케이스(케이스에 `timeout`이 있음)는 제한의 1.3배에서 끊는다. 제한을 넘었지만 1.3배 안에 스스로 끝났으면 한 번 더 돌려 짧은 쪽으로 판정한다. 1.3배에서 끊긴 것은 다시 돌리지 않는다. 시간 초과 결과의 표시 시간은 제한 시간이다. 통과했고 제한의 80% 이상 걸리면 `near: true`를 붙인다.

효율성 제한 시간은 문제마다, 언어마다 다음 식으로 정한다.

```text
제한 = min(언어 상한, max(1.0, ceil(정답 풀이 시간 × 8 / 0.5) × 0.5))
```

- 언어별 상한(초): python 10, javascript 4, java 4, cpp 2, rust 2.
- 바닥은 1.0초, 단위는 0.5초다. 계산 예: 정답 풀이 0.148초면 1.5초, 0.05초면 1.0초, Python 1.7초면 10.0초다.
- 기본 문제는 정답 풀이로 효율성 케이스를 두 번 돌려 잰 시간으로 정해 `limits.json`에 쓴다. 다시 잰 값이 기존 값과 0.5초 이하로 다르고 기존 값으로도 여유가 맞으면 기존 값을 둔다. 여유 기준은 Python 정답 풀이가 제한의 1/3 안, 다른 언어는 1/2 안에 드는 것이다.
- 사용자가 등록한 문제는 큰 입력을 언어 상한으로 한 번 돌려 잰 시간으로 제한을 정하고, 그 언어 하나로 문제에 저장한다.
- 서버가 효율성 케이스에 쓰는 제한 순서는 기본 문제의 `limits`, 등록 문제의 `limits`, 언어 상한, 10초다.
- 블록 확인의 빠른 확인은 효율성 케이스를 뺀다. 기본 문제는 케이스마다 `max(2.0, 그 문제·언어의 효율성 제한)`초로 돌리고, 시간 초과가 한 번이면 멈춘다.

## 실행 환경

- 채점마다 `algoblock-check-` 접두사의 임시 작업 폴더를 만들고, 끝나면 지운다. 제출 파일, 호출 코드, `cases.json`, 큰 인자 파일을 그 안에 쓴다.
- 환경 변수 거르기: 이름에 `KEY`, `TOKEN`, `SECRET`, `PASSWORD`, `CREDENTIAL`이 들었거나, `ALGOBLOCK_`, `ANTHROPIC_`, `OPENAI_`, `XAI_`, `OPENROUTER_`, `AWS_`, `GOOGLE_`, `AZURE_`, `GITHUB_`, `GH_`로 시작하는 변수는 넘기지 않는다. 대소문자는 가리지 않는다. 더해서 `PYTHONUTF8=1`과 `PYTHONIOENCODING=utf-8`을 넘긴다.
- POSIX에서는 새 세션으로 띄우고, 끝나면 프로세스 그룹 전체를 `SIGKILL`로 끝낸다.
- Windows에서는 프로세스를 멈춘 채로 만들어 새 작업 객체에 넣은 뒤 재개한다. 그래서 작업에 들기 전에 자식을 띄울 틈이 없다. 끝나면(정상 종료, 시간 초과, 상한 초과) 작업을 끝내 그 안의 모든 프로세스를 끝낸다. 작업은 `KILL_ON_JOB_CLOSE`라서 앱이 갑자기 죽어 핸들이 닫혀도 모두 끝난다. 처리되지 않은 예외로 죽는 프로그램은 오류 보고 창을 띄우지 않고 바로 끝난다. DLL을 찾지 못하는 것(MinGW 런타임 등) 같은 오류의 창도 뜨지 않는다. 프로세스를 만드는 동안만 앱의 오류 모드(`SetErrorMode`)에 `SEM_FAILCRITICALERRORS`, `SEM_NOGPFAULTERRORBOX`, `SEM_NOOPENFILEERRORBOX`를 더하고 끝나면 되돌린다. 자식이 부모의 오류 모드를 물려받기 때문이다. 콘솔 창은 띄우지 않는다.
- Windows에서 작업 객체를 만들거나 프로세스를 넣지 못하면 작업 없이 실행한다. 이때 결과에 `warning`(까닭)과 `warning_kind`(`no_job`)를 붙인다. 앱은 채점 결과 아래에 실행 제한을 걸지 못하고 돌렸다는 한 줄을 보인다. 시간 제한과 0.25초마다 재는 메모리 상한은 그대로 걸린다. 멈춘 채 만든 프로세스를 재개하지 못하면 끝내고 실행 오류로 남기며 `warning_kind`는 `not_started`다. 앱은 이때 시작하지 못한 테스트가 있다고 알린다. 서버의 표준 오류에도 같은 까닭을 한 번 적는다(창 모드의 설치 파일에는 표준 오류가 없다). 정리는 시간 초과와 상한 초과 때의 `taskkill /F /T`뿐이다.
- Windows에서 `./app` 같은 실행 파일은 작업 폴더의 절대 경로(`app.exe`가 있으면 그것)로 바꿔 부른다. 다른 명령은 PATH에서 찾은 경로로 부른다. `.bat` 같은 `.exe`가 아닌 명령도 이렇게 찾는다.
- 앱이 끝날 때 돌고 있는 채점 실행을 모두 끝낸다.

## 격리 없음

제출 코드는 컨테이너나 OS 샌드박스 안에서 돌지 않는다. 파일과 네트워크 접근을 막지 않는다. 시간, 출력 크기, 메모리, CPU 시간의 제한만 건다. JavaScript의 `vm` 컨텍스트에도 `require`와 `process`를 넘긴다.

같은 채점기가 모델이 만든 풀이와 케이스 생성기도 실행한다. 그 경로는 [보안](security.md)에서 다룬다.

## 알려진 한계

- 제출 코드는 격리되지 않는다. 사용자 권한과 파일, 네트워크 접근을 가진 채 돈다.
- Windows에서 작업 객체를 쓰지 못한 실행(`warning`)에는 CPU 시간 상한, 커밋 메모리 상한, 프로세스 수 상한이 없고, 정상 종료한 주 프로세스의 자식을 남길 수 있다.
- Windows의 CPU 시간 상한은 사용자 모드 시간만 센다.
- Windows의 오류 창 끄기는 프로세스 전체의 오류 모드를 잠깐 바꿨다가 되돌린다. CPython이 확장 모듈을 불러올 때 잠금 없이 오류 모드를 바꾸므로, 그와 겹치면 드물게 되돌린 값이 어긋날 수 있다.
- `setsid`로 새 세션을 만든 자식은 프로세스 그룹 밖이라 끝내지 못한다(POSIX). Windows의 작업에는 이 빈틈이 없다.
- 메모리 상한은 0.25초 간격으로 재므로 짧은 순간의 초과는 놓칠 수 있다.
- 도구 버전은 확인하지 않는다.
- 답이 여럿인 문제는 등록할 때 '답이 여럿일 수 있음'을 켜면 다른 답을 틀렸다고 하지 않는다(맞는지 가리지도 못한다). 켜지 않은 표준 입출력 문제에서는 맞는 풀이도 기대 출력과 다르면 통과하지 못할 수 있다.
- 창을 닫으면 채점 실행을 정리한다. 메뉴의 '끝내기'는 이 정리를 거치지 않을 수 있다. 이때 POSIX에서는 CPU 상한만 남는다. Windows에서는 앱 프로세스가 끝나며 작업 핸들이 닫혀 모두 끝난다.
