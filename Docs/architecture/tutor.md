# 튜터 엔진

튜터 엔진(`app/tutor`)은 요청 하나를 그래프 하나로 처리한다. 이 문서는 에이전트 구성, 요청의 흐름, 블록 확인이 보장하는 것과 보장하지 않는 것을 설명한다.

## 입구

- 공개 진입점은 `Tutor`, `extract`, `IngestError`, `Outcome`, `graph`, `run`이다.
- 요청 종류는 `explain`, `turn`, `followup`, `fill`, `feedback`, `debug`, `prepare` 7개다. 저장은 성공했을 때만 한다. 체크포인터는 쓰지 않는다.
- 모델에서 예외가 나면 그래프 밖에서 오류 응답으로 바뀐다. 저장 노드에 닿지 않으므로 아무것도 저장되지 않는다.

## 에이전트

에이전트는 13개(A1–A13)이고, A13이 디버그다. 한 폴더가 LangGraph 그래프 하나다. 노드 수는 그 그래프의 노드 개수다.

| 표시 | 이름 | 폴더 | 하는 일 | 노드 수 |
|---|---|---|---|---|
| A1 | 문제 읽기 | `ingest/` | 글·파일을 나누고 그림 장을 읽는다(메인 그래프 밖) | 5 |
| A2 | 문맥 불러오기 | `context/` | 저장된 해설·피드백을 찾아 재사용한다 | 2 |
| A3 | 요청 검사 | `request_check/` | 요청을 검사한다. 거절이면 모델을 부르지 않는다 | 1 |
| A4 | 블록 설계 | `plan/` | 뼈대, 풀이 가이드, 블록 나누기, 힌트를 만든다 | 8 |
| A5 | 해설 | `explain/` | 해설을 쓰고 절 제목을 검사한다 | 2 |
| A6 | 생각하는 의자 | `chair/` + `turn/` | 질문으로 생각을 이끄는 대화 | 6 |
| A7 | 가이드 | `guide/` + `turn/` | A6과 같은 그래프. 판정 규칙과 프롬프트만 다르다 | 6 |
| A8 | 꼬리질문 | `followup/` | 꼬리질문에 답한다 | 3 |
| A9 | 블록 채우기 | `fill/` | 블록 코드를 채운다 | 2 |
| A10 | 피드백 | `feedback/` | 제출 결과를 분석해 피드백을 쓴다 | 4 |
| A11 | 나가는 글 검사 | `output_check/` | 나가는 말과 블록 코드를 마지막으로 검사한다 | 2 |
| A12 | 저장과 응답 | `save/` | 저장하고 응답을 만든다 | 3 |
| A13 | 디버그 | `debug/` | 틀린 곳을 같이 찾는다 | 6 |

화면 이름과 코드 이름은 이렇게 대응한다. '튜터의 질문으로' = `chair`(A6), '튜터와 차례로' = `guide`(A7), '틀린 곳 같이 찾기' = `debug`(A13). '혼자 풀기'는 엔진을 쓰지 않는다. 힌트는 저장된 계획의 힌트를 `app/ui/server.py`의 `hint_rows`가 모델 없이 내고, 해설은 실린 것이나 저장된 풀이 가이드다.

## 요청 하나의 흐름

메인 그래프는 `context → request_check → plan → 기능 → output_check → save` 순서다. 기능은 `explain`, `chair`, `guide`, `followup`, `fill`, `feedback`, `debug` 중 하나다.

- `context` 뒤: 오류이거나 저장된 결과가 있으면 끝낸다. 해설이나 같은 제출의 피드백이 있으면 그것을 쓴다. 모델을 부르지 않는다.
- `request_check` 뒤: `prepare`는 계획이 없을 때만 `plan`으로 간다. `debug`는 계획 없이 기능으로 간다. 나머지는 계획이 없을 때만 `plan`으로 간다. 계획을 만든 뒤 사용자가 코드를 먼저 썼어도 다시 짜지 않고 준비해 둔 순서로 시작한다.
- 기능 뒤: 의자가 '사용자 방법으로 다시 짜기'를 청하면 `plan`을 거쳐 기능으로 돌아온다. 한 요청에 한 번만 한다.

## 문제 넣기부터 대화까지

- 문제 읽기(A1)는 등록 화면의 '읽기'가 부르고, 등록할 때 저장소에 넣는다. 문제를 열면 서버가 `prepare`를 뒤 스레드에서 돌린다(모델 연결이 있을 때만).
- 계획(A4)은 `abstract`(뼈대, 이미 있으면 건너뜀), 사용자 코드가 있으면 `assess`, `pick_strategy`, `solve`, `recall`, `draft_blocks`, `check_blocks`, `clean_hints` 순서다.
- `solve`는 문제 글만 보고 풀이 가이드를 만든다. 채점 콜백으로 확인하며, 틀리거나 진입 함수 머리(인자 이름·차례)가 시작 코드와 다르면 다시 만들어 모두 최대 3번 만든다. 머리는 시작 코드에 머리가 있는 함수 방식에서만 보며(여러 줄이어도 괄호가 닫힐 때까지 읽고, C 계열은 형 다음의 마지막 낱말을 이름으로 본다), 다른 머리는 채점기를 부르기 전에 규칙으로 거른다. 세 번 다 통과하지 못하면 `verified=False`로 쓴다. 채점하지 못하면(케이스·채점기·도구가 없거나 인자 형을 다루지 못함) `verified=None`으로 쓰고 다시 만들지 않는다. 확인 값은 통과(`True`), 통과하지 못함(`False`: 실패·시간 초과·컴파일·실행 오류·진입 함수 없음, 또는 머리가 다름), 채점하지 못함(`None`)이다. 저장 칸은 0·1·2(순서대로 `False`·`True`·`None`)다. 정석 가이드는 문제마다 하나이고, 이미 있으면 다시 만들지 않는다. 기본 문제는 실린 정답 코드를 가이드로 쓴다.
- 등록 문제는 단순 풀이와 입력 생성기로 대조한다. 다르면 가운데 급으로 한 번, 그래도 다르면 큰 급으로 한 번 다시 푼다. 맞은 입력은 숨은 케이스나 효율성 케이스가 된다. 블록은 가이드 코드의 이어진 줄 구간이며, 빠짐없이 나누지 못하면 한 번 다시 받고 그래도 안 되면 규칙으로 자른다.
- 대화(A6·A7)는 준비, 판정(말이면 판정, 블록 코드면 코드 확인), 질문 유형 고르기, 말 만들기, 검사 순서다. 내용 없는 짧은 말('모르겠어요', '힌트')은 규칙으로 먼저 가른다. 질문 유형은 규칙 표로 고른다. 의자는 open → clue → trace, 가이드는 blank → tool → shape 순서다. 두 방식 모두 말로 맞혀도 다음 블록을 열지 않고(`write`, 고정 말), 블록 코드 확인이 통과하거나 넘어가기·채우기를 했을 때 연다.
- 말 판정은 `[check]` 한 줄이다. 글자는 Y(맞음), N과 빠진 신호 번호(아님), D(의자만. 계획과 다르지만 풀리는 방법), A(답이나 답 코드를 달라는 요청), O(문제와 무관한 말), Q(자기 생각이 아니라 튜터 말·문제·문법·개념을 되묻는 말)다. 예전 글자 W(낱말 뜻)는 Q로 읽는다. 자기 생각을 물음 꼴로 낸 말은 Q가 아니라 판정 기준대로 가른다. Q면 `term` 차례로 그 물음에 먼저 답하고(문법은 이 문제와 상관없는 작은 예로 보이고, 이 블록의 답은 말하지 않는다) 직전 질문으로 돌아간다. 모델 호출은 판정 1번과 말 만들기 1번이고, 열린 블록 수와 힌트 번호는 그대로다. A·O면 고정 앞말 뒤에 다음 힌트를 낸다.
- 블록을 여는 말과 내용 없는 답에는 계획의 힌트를 1, 2, 3 차례로 내고, 다 내면 고정 말을 낸다. 모델을 부르지 않는다. 의자는 지금 블록의 이름을 숨기고 종류(변수, 반복, 조건, 분기)만 알린다.

## 블록 확인이 보장하는 것

블록 확인은 사용자가 적은 블록 코드를 튜터의 가이드 코드에 끼워 판정한다. 기록 값은 'Y'(통과), 'N'(이어지지 않아요, 또는 실행이 뒷받침하지 못한 실패), '?'(확인 전)다. 판정 차례는 다음과 같다.

1. 이름 바꾸기 표를 적용한 계획 코드와 줄 끝 공백·빈 줄만 다른 글자 그대로의 같음이면 통과다. 실행하지 않는다. 풀이 가이드가 예시를 통과했을 때(검증됨)만이다.
2. 채점 함수가 없을 때만 지난 판정을 다시 쓴다. 지난 판정이 Y·N이고 코드가 같을 때만이다. 지난 N은 읽고 거절한 것으로 다시 쓰여 확인 전이 된다. '?'였던 판정은 모델이 다시 본다.
3. 튜터 코드로 이을 블록이 남았는데 풀이 가이드를 믿을 수 없으면 실행하지 않는다(예외 ④). 채점하지 못했던 가이드는 지금 다시 채점해 통과하면 믿고, 채점하지 못하면 4번으로 보낸다. 믿을 수 있으면 실행 판정을 한다. 실행 프로그램은 방금 적은 블록을 넣고, 사용자가 적어 통과했거나 확인 전인 블록은 저장된 글을 넣고, 나머지는 계획 코드를 넣는다. 효율성 케이스는 빼고(`quick`), 첫 시간 초과에서 멈춘다. 통과하면 Y다. 통과하지 못하면 내가 쓴 블록을 모두 이은 프로그램(튜터 코드 없이, 모아서 실행과 같은 글)을 한 번 더 돌려, 숨은 테스트까지 통과하면 Y다. 앞 블록에 빈 칸이 있거나 공개 예시뿐인 문제면 이 길로 Y를 주지 않는다. 그렇지 않으면 짝을 다 시도했을 때 N('이어지지 않아요')이고, 시간 한도로 다 시도하지 못했거나 튜터가 이어 쓰는 이름을 내 코드에서 찾지 못했으면 '?'(확인 전)다. 컴파일·실행 오류로 끝났고 중괄호 언어에서 열어 둔 괄호 수가 계획과 다르면 고정 안내를 덧붙인다(N은 그대로).
4. 실행하지 못하면 모델이 코드를 읽고 판정한다(예외 ②).

화면은 기록과 마지막 확인 결과로 칸 상태를 그린다. 기록 Y는 '통과'(숨은 테스트가 없는 문제는 '예시 통과')다. 실행으로 뒷받침된 N은 '이어지지 않아요'다. '?'이거나 실행이 뒷받침하지 못한 N은 '확인 전'이다. 칸 글이 저장된 글과 다르면 '확인 전'이고, 앞 블록이 바뀌어 물린 칸은 '확인 전 · 앞 블록이 바뀌었어요'다. 이어 돌린 실행이 통과하지 못했다는 것은 틀렸다는 뜻이 아니다. 고칠 곳이 있거나 튜터와 다른 방식으로 쓴 것이다.

아래 '약속' 1–4는 블록 확인이 지키는 것이고, '예외' ①–④는 그 약속을 그대로 지키지 못해 다르게 처리한 경우다.

### 약속 1. 통과는 실행이 정한다. 조건부로만 성립한다.

- 실행 결과가 `passed`일 때만 실행 판정이 Y다.
- 예외 ①: 1번의 글자 그대로 같은 길은 실행 없이 통과한다. 근거인 풀이 가이드가 예시를 통과했을 때만 성립한다.
- 예외 ②: 블록 코드 확인에서 실행하지 못하면(도구 없음, 채점기가 다루지 못하는 인자 형, 케이스 없음) 모델이 판정한다. 통과는 '?'로, 실패는 틀린 수에 넣지 않는 N으로 저장하고(화면은 둘 다 '확인 전'), 실행하지 못해 코드를 읽고 본 판단이라고 말한다. 진행은 막지 않는다.
- 예외 ③: 공개 예시로만 돌아 통과했으면(숨은 테스트가 없다) Y로 저장하되 '공개 예시로만 확인했어요.'를 붙인다.
- 예외 ④: 풀이 가이드가 없거나 예시를 통과하지 못했으면, 다른 블록 가운데 튜터 코드로 이어야 할 블록이 있을 때는 실행하지 않는다. 그 칸은 '?'(확인 전)로 저장하고 틀린 수에 넣지 않으며, 튜터의 풀이를 이 문제의 예시로 확인하지 못했다고 말한다. 다른 블록이 모두 사용자 코드(통과했거나 확인 전)이면 돌린다.
- 블록 채우기는 이어 돌려 통과했을 때만 'Y'로 저장한다. 통과하지 못하면 계획 코드(이름을 바꾸지 않은 글)로 채우고 '?'로 둔다. 채점 함수가 없거나 채점하지 못했거나 풀이 가이드를 믿을 수 없으면 '?'로 두고 까닭을 말한다.

### 약속 2. 블록은 한 곳에서 이어 붙인다. 성립한다.

- 확인 실행용 `spliced`와 화면 모으기용 `composed_parts`가 같은 `framed` 함수로 블록을 감싼다.
- 화면 모으기는 서버 `/api/compose`가 `composed_parts`를 부른다.
- 차이: 모으기는 빈 블록을 빼고 블록마다 `# 블록 n · 이름` 주석 한 줄을 넣는다. 확인 실행은 빈 블록 자리에 계획 코드를 넣는다.

### 약속 3. 앞 블록이 바뀌면 뒤 블록의 통과를 물린다. 확인할 때만 성립한다.

- 블록의 저장된 글과 해시가 다르면, 그 뒤의 'Y' 블록을 모두 '?'로 바꾼다. 글과 진행 위치는 그대로 둔다. 판정 결과와 관계없이 물린다.
- 앞 블록을 다시 확인해 실패하면 그 블록은 'N'이 아니라 '?'가 된다. 틀린 수에도 넣지 않는다.
- 빈틈: 물리기는 블록 코드 확인에서만 일어난다. 앞 블록을 '이 블록 채우기'로 바꾸는 길에는 뒤 블록을 물리는 코드가 없다.

### 약속 4. 튜터는 한 일을 그대로 말한다. 대부분 성립한다.

- 물린 뒤에는 "뒤 블록 n개는 다시 확인해 주세요."라고 블록 수를 말한다.
- 계획 코드로 이은 블록이 있거나 어림한 이름 짝으로 돌렸으면 그 사실을 말한다("참고로, …"). 굳은 짝으로 다른 이름에 통과하면 이 문제에서 처음일 때만 알린다.
- 블록 채우기도 짐작한 이름, 계획 이름으로 채운 사실, 통과하지 못한 사실을 말한다.
- 빈틈: 글자 그대로 같은 길의 통과는 실행 없이 통과했다고 말하지 않는다(검증된 풀이와 같은 글이다). 모델이 판정한 통과와 거절은 실행하지 못했다고 앞말로 말한다. N이면 고정 앞말과 힌트를 낸다.

## 이름 짝

- 이름 짝은 계획 블록이 내놓는 이름(뒤 블록의 계획 코드가 읽는 이름)을 사용자 코드의 어느 이름이 맡는지 정한 것이다.
- 굳은 짝은 만드는 문장의 꼴이 같고, 그 꼴이 양쪽에 하나씩뿐일 때다. 같은 꼴이 둘 이상이면 나온 순서를 첫 가정으로만 쓴다(무리). 매개변수 순서가 다르면 따로 표시한다.
- 확인 실행은 첫 가정으로 돌린다. 통과하지 못하면 다른 후보와 다른 순서를 시간 한도 안에서 돌린다. 통과하면 그 짝을 `renames_json`에 저장해 뒤 블록의 확인과 채우기에 쓴다.
- 짝을 찾지 못하면 튜터는 사용자에게 뒤 블록이 쓰는 값의 이름을 맞춰 달라고 한다. 이름을 맞추지 못해 결론을 내지 못한 것은 '확인 전'이고 틀린 수에 넣지 않는다.

## 모델 글의 규칙 검사

튜터가 쓴 말풍선은 검사를 거친다.

- 검사 항목: 비었음, 코드 펜스, 금지 표현(아래 15개. 문제 글 인용은 제외), 동의나 칭찬으로 시작, 3문장 초과, 질문으로 끝나지 않음, 질문 여럿, 참고 코드 줄이 그대로 나옴, 지금 블록의 답을 말한 평서문, 뒤 블록 이름, 근거 없는 따옴표 인용, 3인칭 메모, 영어 다섯 낱말 이상.
- 금지 표현은 `app/tutor/common/talk_rules.py`의 `BANNED`다: 정답, 맞아요, 맞습니다, 틀렸어요, 완벽, 훌륭, 잘했어요, 좋아요, 좋은 질문, 좋은 생각, 전적으로, 말씀하신 게 맞, 정말 그렇, 분명히 그렇, 당연히.
- 고칠 수 있는 위반은 모델을 다시 부르지 않고 규칙으로 고친다(`repair`). 사용자 말을 되받는 첫 절 지우기, 지금 블록의 답을 말한 평서문 지우기, 근거 없는 따옴표 지우기, 마지막 물음표 뒤 자르기, 질문은 마지막 하나만 남기기, 뒤 세 문장만 남기기가 여기에 든다.
- 고칠 수 없는 위반이 있거나 고친 뒤에도 위반이면 질문 유형별 고정 대체 질문을 낸다. 모델을 다시 부르지 않는다. 대체 질문을 낸 까닭은 로그와 표준 오류에 남긴다.
- 계획의 힌트가 같은 검사에 걸리면 그 블록만 한 번 다시 받고, 또 걸리면 비운다. 저장 힌트와 고정 문구는 계획 때 검사하므로 대화 때 다시 검사하지 않는다.
- 해설(A5)은 절 제목이 맞지 않거나 빈 절이 있으면 요청을 실패시킨다. 피드백(A10)은 힌트나 조언에 코드 펜스가 있으면 실패시킨다. 말풍선에 코드 펜스가 남으면 A11이 `invalid_output`으로 실패시킨다.

이 검사는 낱말 목록과 정규식 같은 글 모양 규칙으로만 본다. 기법 낱말 숨기기는 프롬프트 지시일 뿐 말풍선을 막는 규칙이 아니다([온톨로지](ontology.md)).

## 저장

- 요청 하나가 저장하는 것은 대화 말, 질문 유형, 디버그 진단, 문제 뼈대, 계획, 열린 블록 수, 해설, 피드백, 블록 판정, 풀이 가이드다. 저장은 한 번에 하며, 실패하면 `store_failed`로 응답한다([데이터 폴더](data.md)).
- 새 계획을 저장하면 벡터 색인에 문제를 넣는다. 색인 실패는 무시한다. 사용자 방법으로 짠 계획의 가이드는 정석 가이드를 덮지 않고 따로 둔다.

## 알려진 한계

- 글자 그대로 같은 길은 실행 없이 통과시킨다. 그 근거인 가이드는 예시를 통과한 것만 쓴다(`verified=True`).
- 블록 코드 확인에서 채점 함수나 케이스가 없거나 채점하지 못하면 통과 여부를 모델이 읽고 정하며, 그 통과는 '?'로 저장된다. 블록 채우기는 이어 돌려 통과했을 때만 'Y'로 저장하고, 채점하지 못하면 '?'로 저장된다.
- 앞 블록을 '이 블록 채우기'로 바꾸면 뒤 블록이 물리지 않는다.
- 글자 그대로 같은 길로 통과한 것은 실행 없이 통과했다고 말하지 않는다.
- 블록 확인은 효율성 케이스를 뺀다. 효율성은 이 확인에서 가려지지 않는다.
- 짝 찾기 재시도는 첫 실행부터 6초가 지나면 새로 시작하지 않는다.
- 말풍선 검사는 글 모양 규칙이다. 규칙에 걸리지 않고 원칙을 어기는 말은 막지 못한다.
- 튜터와 다른 구조로 쓴 맞는 블록(다른 자료구조, 다른 입력 읽기, 한 블록에 더 많은 일, 직접 닫은 괄호)은 '이어지지 않아요'나 '확인 전'이 될 수 있다. 틀렸다는 뜻이 아니다. '이대로 넘어가기'로 다음 블록을 열 수 있고, 코드를 끝까지 쓴 뒤 실행이나 제출로 확인한다.
- 피드백은 블록 코드 확인에 낸 글의 판정 표시로 확인 답을 막힘에서 뺀다. 표시가 없는 옛 기록에서는 '확인 전'으로 끝난 확인도 막힌 답으로 센다.
- '끝까지 내 방식으로 쓰기'를 켜면 지금 블록은 확인 전으로 두고 남은 블록을 모두 연다(통과를 만들지 않는다). 그 뒤로는 블록마다의 실행 확인이 없어, 틀린 줄은 모아서 실행·제출에서 한꺼번에 드러난다.
