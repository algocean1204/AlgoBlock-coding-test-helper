# 기본 문제 만들기 규칙

검사·묶기·PR의 순서는 [Docs/contributing/add-builtin-problem.md](../../../Docs/contributing/add-builtin-problem.md)에 있다. 이 문서는 문제를 쓰는 규칙이다.

기본 문제는 주제 15개 × 5단계 = 75개다. 문제 하나가 폴더 하나다: `ui/problems/<주제>/<단계>_<이름>/`.
본보기는 `hash/1_popular_shelf/`다. 새 문제를 쓰기 전에 그 폴더의 파일을 모두 읽는다.

검사(모델을 부르지 않는다. `app`에서):

```bash
python3 ui/problemkit.py check ui/problems/<주제>            # 주제 폴더 전체
python3 ui/problemkit.py check ui/problems/<주제>/<단계>_<이름>  # 문제 하나
```

`통과`가 나와야 실을 수 있다. 통과하면 폴더에 `cases.json`(얼린 케이스와 기대 결과)과, 효율성 케이스가 있으면 `limits.json`(언어별 제한 시간)이, 언어 함정 풀이가 있으면 `lang.json`이 생긴다. 다른 언어 정답 풀이(`solution.java` 등)와 그 언어의 함정 풀이까지 검사하고 그 제한을 재려면 `--langs`를 붙인다. 검사는 끝에 함정 목록(`lang_traps.json`)도 한 번 본다.

## 목표

- 사용자가 주제마다 1단계부터 5단계까지 차례로 풀면서, 같은 키워드가 조금씩 모습을 바꿔 나오는 것을 겪는다.
- 실전에서 비슷한 표현을 보면 "이건 그 유형이다" 하고 바로 알아채게 된다(실전 신호).
- AI 없이도 채점이 된다. 그래서 채점 케이스가 틀린 풀이와 느린 풀이를 빠짐없이 걸러야 한다.

## 주제

| 키 | 이름 | 다루는 것 |
| --- | --- | --- |
| `hash` | 해시 | 딕셔너리, 집합, 개수 세기, 묶어서 세기, 경우의 수 곱 |
| `stack_queue` | 스택/큐 | 스택, 큐, 덱, 짝 맞추기, 단조 스택 |
| `heap` | 힙 | 우선순위 큐, 가장 작은 것 꺼내기, 두 힙, 작업 순서 정하기 |
| `sort` | 정렬 | 내장 정렬, 비교 기준 정하기, 여러 기준, 정렬 뒤 한 번 훑기 |
| `brute_force` | 완전탐색 | 전수 반복, 순열·조합, 부분집합, 재귀 백트래킹 |
| `greedy` | 탐욕법 | 정렬 뒤 고르기, 구간 고르기, 바꿔치기 논증이 되는 선택 |
| `dp` | 동적계획법 | 1·2차원 표, 점화식 세우기, 구간 DP, 배낭 |
| `dfs` | 깊이 우선 탐색 | 재귀·스택 DFS, 연결 요소, 경로 만들기, 가지치기 |
| `bfs` | 너비 우선 탐색 | 큐 BFS, 최소 단계, 격자 최단 거리, 상태를 늘린 BFS |
| `dijkstra` | 다익스트라 | 가중치 최단 경로, 우선순위 큐, 여러 출발점, 상태를 늘린 최단 경로 |
| `binary_search` | 이분탐색 | 값 찾기, 하한·상한, 답을 정해 놓고 되는지 확인하기 |
| `graph` | 그래프 | 유니온 파인드, 위상 정렬, 최소 신장 트리, 플로이드 |
| `two_pointer` | 투 포인터·누적 합 | 투 포인터, 슬라이딩 윈도우, 1·2차원 누적 합 |
| `simulation` | 시뮬레이션 | 격자 이동·회전, 시간 흐름대로 상태 바꾸기, 규칙대로 반복 |
| `implementation` | 구현 | 문자열 쪼개기·바꾸기, 규칙 여럿을 순서대로 적용, 날짜·시간·진수 계산, 자료 변환 |

대회용 기법(세그먼트 트리, 네트워크 플로우 등)은 쓰지 않는다. 기출에 나오는 수준까지만.

## 단계

| 단계 | 뜻 | 풀려면 알아야 하는 것 |
| --- | --- | --- |
| 1 | 개념: 그 주제의 도구 하나를 그대로 쓰면 풀린다 | 도구 하나의 쓰는 법 |
| 2 | 기본 변형: 같은 도구에 조건이 하나 붙는다 | 도구를 쓰면서 조건 하나를 따로 처리하는 법 |
| 3 | 응용: 문제 글에서 그 주제임을 스스로 알아채야 하고, 느린 풀이는 시간이 모자란다 | 글을 보고 도구를 고르는 것, 입력이 커질 때의 풀이 |
| 4 | 심화: 생각 두 가지를 이어야 한다 | 두 생각을 한 풀이로 잇는 것 |
| 5 | 고득점: 4단계에 함정이나 상태가 하나 더 붙는다 | 4단계의 풀이에 함정이나 상태를 하나 더 다루는 것 |

다섯 문제는 한 사다리다. 앞 문제에서 배운 것 위에 한 가지씩 더한다(`ladder`에 무엇이 더해졌는지 적는다).
이야기와 자료의 모양은 문제마다 다르게 한다(다섯 문제가 모두 "숫자 배열"이면 안 된다).

## 저작권

다른 곳의 문제 글·문장·숫자·예시를 옮기지 않는다. 유형(무엇을 어떻게 푸는 문제인가)만 참고하고, 이야기·문장·변수 이름·숫자·예시는 새로 쓴다. 참고한 유형이 있으면 `source_type`에 일반 유형 이름(예: "최소 신장 트리")만 적는다. 다른 곳의 문제 제목은 적지 않는다.

## 폴더에 넣는 파일

| 파일 | 내용 |
| --- | --- |
| `problem.json` | 문제 글과 딸린 정보(아래) |
| `solution.py` | 정답 풀이. `def solution(...)`. 가장 큰 입력에서도 약 3초 안에 끝난다. 초보자가 읽고 따라 쓸 수 있는 직관적인 코드(기교 없이, 사고 순서대로, 표준 라이브러리만) |
| `brute.py` | 문제 글의 정의를 글자 그대로 옮긴 풀이. 빠를 필요가 없다. `solution.py`와 다른 방법이어야 한다(같은 실수를 같이 하지 않게) |
| `wrong_1.py` … | 배우는 사람이 실제로 하는 흔한 오답 3개 이상. 첫 줄은 `# 틀린 까닭: …`. 채점 케이스가 모두 걸러야 한다 |
| `slow_1.py` … | 답은 맞지만 느린 풀이(처음 떠올리기 쉬운 방법). 첫 줄은 `# 느린 까닭: …`. 그 문제의 Python 제한(아래 제한 시간)에서 효율성 케이스를 시간 초과해야 한다. 효율성 케이스가 없으면 두지 않는다 |
| `gen.py` | 채점 입력을 만드는 코드(아래) |
| `ready.json` | 풀이 가이드·블록·힌트. 새로 쓰지 않는다: `ui/make_builtin.py build`가 모델로 만들어 쓰고, 검수에서 문장만 고친다(아래) |
| `limits.json` | 효율성 케이스의 언어별 제한 시간(초). `{"python": 1.5, "java": 1.0, …}`. 새로 쓰지 않는다: 검사가 정답 풀이의 시간을 재서 쓴다(아래 제한 시간). 효율성 케이스가 없으면 없다 |
| `lang_1.<확장자>` … | (없어도 된다) 그 언어의 정답 풀이에 언어 함정 하나만 넣은 풀이. 언어마다 3개까지. 첫 줄은 함정의 id(아래 언어 함정). 채점 케이스에서 실제로 떨어져야 한다 |
| `lang.json` | 언어 함정 풀이가 어느 케이스에서 어떤 상태로 떨어졌는지(틀린 답이면 돌려준 값까지). 새로 쓰지 않는다: 검사가 쓴다. 함정 풀이가 없으면 없다 |

### 제한 시간

효율성 케이스의 제한은 문제마다·언어마다 다르다. 검사가 그 언어의 정답 풀이로 효율성 케이스를 두 번 돌리고, 가장 오래 걸린 케이스의 시간(두 번 가운데 짧은 쪽)에서 정한다.

```
제한 = min(언어별 상한, max(1.0초, 정답 풀이 시간 × 8을 0.5초 단위로 올린 값))
```

- 언어별 상한은 `ui/casegen.py`의 `LIMIT`(Python 10초, JavaScript·Java 4초, C++·Rust 2초). 배수 8, 바닥 1.0초, 단위 0.5초도 같은 파일에 있다.
- 예: 정답 풀이가 0.148초 → 1.5초. 0.05초 → 1.0초. Python 1.7초 → 10초(상한).
- 다시 잰 값이 지금 `limits.json`의 값과 0.5초 이하로만 다르고 지금 값으로도 여유가 지켜지면 지금 값을 둔다(다시 잴 때마다 파일이 바뀌지 않게).
- `--langs` 없이 검사하면 Python만 다시 재고, 다른 언어의 값은 그대로 둔다.
- 검사 규칙: 정답 풀이는 제한의 1/3(Python)·1/2(다른 언어) 안에 끝나야 한다(배수 8이라 저절로 지켜지고, 상한에 걸린 문제에서만 걸릴 수 있다). `slow_*.py`는 이 Python 제한에서 효율성 케이스를 시간 초과해야 한다.
- 서버는 기본 문제의 효율성 케이스를 이 값으로 채점한다(없는 언어는 `LIMIT`). 정확성 케이스는 10초다.

### 언어 함정

해설의 정답 코드 위에 고른 언어에서 조심할 것을 보인다(예: Java에서 큰 합을 `int`에 담으면 넘친다). 이 앱의 채점기로 그 문제에서 실제로 틀리는 것이 확인된 것만 보인다.

- 보일 글은 `ui/problems/lang_traps.json` 한 곳에만 있다. 언어마다 12개까지다. 문제 폴더에서는 글을 쓰지 않고 이 목록의 id를 고른다.
- 문제 폴더의 `lang_<번호>.<확장자>`는 같은 언어의 정답 풀이(`solution.<확장자>`)에 그 실수 하나만 넣은 풀이다. 첫 줄은 그 언어의 주석으로 쓴다.

```java
// 언어 함정: java.int_multiply @ "n은 1 이상 500,000,000 이하" "chargers의 원소는 1 이상 100,000 이하"
class Solution { … }
```

- `@ "…"`는 없어도 된다. 쓰면 문제 글이나 제한사항에 글자 그대로 있는 구절이어야 하고, 둘까지 쓸 수 있다. 화면에 '이 문제에서 걸리는 곳: “…”'으로 함께 보인다.
- 구절은 그 실수가 이 문제에서 왜 드러나는지(무엇이 커지거나 깊어지는지) 보이는 가장 짧은 말로 고른다. 제한사항 한 줄 전체보다 그 안의 범위를 고르고, 두 값의 곱처럼 둘이 함께 커지는 것이면 둘을 적는다.
- 목록의 항목은 다음 칸으로 이루어진다. `what`과 `fix`는 80자까지다.

| 칸 | 뜻 |
| --- | --- |
| `id` | `<언어>.<이름>`(소문자·숫자·`_`) |
| `what` | 무슨 일이 생기나. 백틱으로 감싼 이름을 하나 이상 쓴다(실수한 코드의 이름이나 `RecursionError` 같은 결과 이름). 고치는 이름(`right`)은 쓰지 않는다 |
| `fix` | 어떻게 고치나 |
| `code` | 실수한 코드에 새로 나타나는 이름들(예: `size_t`, `>>`). 없어도 된다 |
| `right` | 정답 풀이가 그 실수를 막는 이름의 대안들(예: `getOrDefault`, `containsKey`, `merge`). 그중 하나가 정답 풀이에 있으면 된다 |
| `recipe` | 정답 풀이를 어떻게 바꿔 증명 풀이를 만드나 |
| `varies` | (있으면 `true`) 결과가 정해지지 않은 동작(C++의 `int` 넘침, 범위 밖 읽기)이라 떨어지는 케이스·상태가 컴파일러와 기기마다 다를 수 있다. `what`도 그렇게 쓴다 |
| `shape` | (없어도 된다) 실수의 모양을 적은 정규식. 주석을 뺀 코드에 맞춘다. 이름만으로는 다른 코드와 가를 수 없을 때 둔다(예: 거꾸로 도는 `size_t` 반복). 있으면 튜터는 이름 대신 이것으로 사용자 코드를 본다. `varies` 함정은 이것이 없으면 튜터가 후보로 내지 않는다 |

- 함정은 언어의 일반 사실이어야 한다. 한 문제에만 맞는 글이나 이름을 쓰지 않는다. 다른 문제가 같은 실수를 다른 방법으로 막았으면 `right`에 대안을 더한다. 목록에 없는 함정을 찾았으면 먼저 목록에 더하고, 그 함정을 증명하는 풀이를 함께 낸다.

검사가 보는 것:

- 첫 줄의 id가 그 언어의 목록에 있고, 구절이 문제 글에 있다. 문제·언어마다 3개까지이고 같은 함정을 두 번 쓰지 않는다.
- 정답 풀이와 견주어 넣은 줄과 지운 줄이 각각 6줄 이하다.
- 바꾼 줄에 그 함정의 표시가 있다. 넣은 줄에만 있고 지운 줄에는 없는 `code` 이름, 또는 지운 줄에만 있고 넣은 줄에는 없는 `right` 이름이다. 한 글자 기호와 어느 풀이에나 흔한 낱말(`for`, `if`, `get`, `int` 등, `problemkit.COMMON`)은 표시로 세지 않는다. 목록의 항목마다 표시로 쓸 수 있는 이름이 하나는 있어야 한다.
- 정답 풀이에 `right`의 대안 가운데 하나가 있다.
- `shape`가 있으면 정규식이고, 증명 풀이에는 맞고 정답 풀이에는 맞지 않는다.
- 증명 풀이가 케이스 하나 이상에서 떨어진다(틀림, 실행 오류, 시간 초과). 모든 케이스를 통과하면 그 문제에서는 증명되지 않은 것이라 실패다. 컴파일되지 않는 풀이도 실패다.
- 목록의 항목 가운데 어느 문제의 증명 풀이도 쓰지 않는 것이 있으면 실패다(증명 없는 글은 두지 않는다).
- Python 함정 풀이는 늘 돌리고, 다른 언어는 `--langs`를 붙였을 때 돌린다. 통과하면 `lang.json`에 어느 케이스에서 어떤 상태로 떨어졌는지(`fails`. `varies` 함정은 떨어졌다는 것만), 틀린 답을 낸 케이스마다 돌려준 값(`outs`. 40자를 넘으면 지문)과, 증명 풀이 본문·케이스의 지문을 쓴다. 건너뛴 케이스는 적지 않는다. 본문이나 케이스가 바뀌었는데 다시 돌리지 않았으면 검사에 걸린다. 묶을 때는 실을 언어의 함정만 이 파일에서 싣는다.

### ready.json

손으로 고쳐도 되는 칸과 빌드가 싣기 전에 보는 것은 [Docs/contributing/add-builtin-problem.md](../../../Docs/contributing/add-builtin-problem.md)에 있다. `ui/builtin.json`은 묶은 결과물이라 고치지 않는다.

```json
 "pitfalls": ["흔한 실수"],
 "ladder": "앞 단계 문제에 무엇이 더해졌는가 한 문장",
 "source_type": "참고한 일반 유형 이름(다른 곳의 문제 제목이 아니다). 없으면 빈 글"
}
```

- 형: `int`, `long`, `bool`, `string`과 그 배열 `[]`, 2차원 배열 `[][]`. 이 밖의 형은 쓸 수 없다(5개 언어의 채점기가 이 형만 안다). 실수(`double`)는 쓰지 않는다.
- `long`의 값과 답도 9,007,199,254,740,991(2^53 - 1) 이하여야 한다. JavaScript의 수는 그 위로 정확하지 않아 맞는 풀이가 틀리게 나온다. 넘을 것 같으면 제한을 줄이거나 나머지를 구하게 한다. 풀이 도중의 계산(곱)이 2^53을 넘는지도 본다(나머지 연산 문제에서 두 수의 곱이 10^18에 이르면 JavaScript는 BigInt가 필요하다 — 피할 수 있으면 피하고, 못 피하면 `pitfalls`에 적는다).
- 값이나 답이 2,147,483,647을 넘을 수 있으면 `long`이다(Java, C++, Rust에서 넘친다). 합·곱·경우의 수를 꼭 확인한다.
- `examples`는 3개. 작고, 서로 다른 경우를 보여 준다. 반복 횟수가 10억인 예시처럼 `brute.py`·`slow_*.py`가 끝내지 못하는 예시를 꼭 보여 주고 싶으면 그 예시에 `"big": true`를 적는다(그 예시는 두 풀이 대조에서 빠진다. 답을 `note`에서 손으로 따질 수 있어야 한다). 기대 결과는 적지 않는다(`solution.py`가 정한다).
- `signals`는 2~4개. `phrase`는 본문이나 제한사항에 **글자 그대로** 있어야 한다. `means`는 답을 통째로 말하지 않고, "이 표현 → 이 도구·이 생각"을 가르친다. 효율이 걸린 문제는 입력 크기 표현도 신호로 넣는다.
- `pitfalls`의 실수가 `wrong_*.py`로 있어야 한다.
- `signals.means`·`pattern`·`learn`·`pitfalls`·`ladder`는 사용자가 고른 언어와 상관없이 같은 글로 보인다. 한 언어에만 있는 낱말(예외 이름, `dict`·딕셔너리·`heapq` 같은 내장 이름)을 쓰지 않는다. '해시 표', '우선순위 큐'처럼 개념으로 쓴다. 검사(`problemkit.language_bound`)가 걸러 낸다.

### 문제 글 규칙

- 문체: "~합니다"로 쓰고, 함수 방식은 "~을 return 하도록 solution 함수를 완성하세요"로 과제를 준다.
- 이 글만 읽고 풀 수 있어야 한다. 다르게 읽힐 곳이 없어야 한다:
  - 번호·위치가 0부터인지 1부터인지, 구간의 끝이 포함인지.
  - 같은 값이 여럿일 때 어느 것을 고르는지, 답이 여럿일 때 어느 것을 돌려주는지(순서까지 하나로 정한다).
  - 입력이 정렬되어 있는지, 겹치는 값이 있는지, 비어 있을 수 있는지.
  - 없을 때·불가능할 때 무엇을 돌려주는지.
- 제한사항의 범위와 `gen.py`가 만드는 값이 맞아야 한다. 제한사항의 최댓값을 효율성 케이스가 실제로 쓴다.
- 반환값은 하나로 정해진다(실수 오차, 순서 자유 같은 것이 없다).
- 변수 이름은 영어 소문자, 뜻이 드러나게.

### gen.py

```python
LARGE = 2                      # 효율성 케이스 수(0~3)

def small(rng):                # 정확성 케이스 12~20개: 인자 목록의 목록
def medium(rng):               # (없어도 된다) brute.py로는 못 돌리는 크기의 정확성 케이스 8개까지
def random_small(rng):         # 무작위 작은 입력 하나(인자 목록). 두 풀이 대조에 300번 쓴다
def valid(*args):              # (없어도 된다) 인자가 제한사항에 맞으면 True. 있으면 모든 케이스와 무작위 입력을 이것으로 검사한다
def large(rng, index):         # index번째 효율성 케이스의 인자 목록
```

- 난수는 인자로 받은 `rng`만 쓴다(`ui/casegen.py`의 `Rng`: `randint(low, high)`, `chance(분자, 분모)`, `choice(목록)`, `shuffle(목록)`, `sample(목록, 개수)`, `distinct(low, high, 개수)`, `word(길이, 글자들)`). `random`, `time` 같은 모듈을 import하지 않는다. 큰 입력은 사용자가 채점할 때마다 이 코드로 다시 만들기 때문에 언제 돌려도 같은 값이 나와야 한다.
- `valid`: 제한사항(길이, 값의 범위, 서로 다름, 글자 종류, 날짜의 앞뒤 등)을 코드로 적어 둔다. 손으로 넣은 케이스가 제한사항을 벗어나는 실수를 잡아 준다. 제한사항이 여러 줄인 문제에는 두기를 권한다.
- 실행할 때마다 달라지는 것에 기대지 않는다: 문자열이 든 집합(`set`)을 도는 순서는 파이썬을 켤 때마다 바뀐다. 집합은 `sorted()`로 돌고, `id()`·시각·환경을 쓰지 않는다(검사기가 해시 씨앗을 바꿔 가며 같은 입력이 나오는지 본다).
- `small`: 경계를 손으로 넣는다(가장 작은 입력, 가장 큰 값, 모두 같은 값, 이미 정렬된 것, 답이 없는 것, 답이 처음·끝에 있는 것 등). 그 뒤에 무작위 몇 개. 케이스 하나는 JSON으로 2,000자 안쪽(틀렸을 때 사용자에게 보여 줄 수 있는 크기).
- `brute.py`와 `slow_*.py`는 `small`의 케이스를 모두 10초 안에 맞게 풀어야 한다. 그래서 `small`은 `brute.py`가 감당하는 크기로 둔다.
- `medium`: `brute.py`로는 못 돌리지만 화면에 보여 줄 수 있는 크기(2,000자 안쪽)의 정확성 케이스. 답이 `int`를 넘는 경우, 나머지 연산이 실제로 일어나는 경우처럼 **값이 커야 드러나는 실수**를 '시간 초과'가 아니라 '틀림'으로 잡으려고 둔다. 기대 결과는 `solution.py`만으로 정해지므로, 답을 손으로 따져 볼 수 있는 모양(예: 모두 같은 값, 규칙적인 값)을 섞는다. `brute.py`·`slow_*.py`는 이 케이스를 돌리지 않는다.
- `random_small`: `brute.py`가 금방 끝나는 아주 작은 입력. 값의 범위를 좁혀 겹침·동점 같은 까다로운 경우가 자주 나오게 한다. 결과가 한쪽으로 쏠리지 않게 한다.
- `large`: 제한사항의 최대 크기. 느린 풀이가 가장 오래 걸리는 모양으로 만든다(일찍 끝나 버리지 않게). JSON으로 2,500,000자 안쪽이 기준이다(검사기가 본다). 낱개 값(수·글)으로 세면 대략 20만~30만 개다.
- 반환값도 크기를 본다. 채점기는 표준 출력이나 표준 오류가 4,000,000바이트를 넘으면 끝낸다(`output_limit`). 기본 문제의 가장 큰 답은 1MB 안쪽으로 만든다(`app/judge/common.py`의 `OUTPUT_LIMIT` 주석). 큰 입력에서 긴 배열이나 긴 문자열을 돌려주는 문제는 그 안에 들게 하고, 되도록 값 하나(합, 개수, 최댓값)를 돌려주게 설계한다(효율성 케이스의 기대 결과가 `cases.json`에 통째로 저장된다).
- 1~2단계에서 더 느린 자연스러운 풀이가 없으면 `LARGE = 0`으로 두고 `slow_*.py`를 두지 않는다. 3단계부터는 효율성 케이스가 있어야 한다.

## 다 쓴 뒤 스스로 확인

1. `python3 ui/problemkit.py check ui/problems/<주제>`가 다섯 문제 모두 `통과`.
2. 문제 글만 다시 읽고(풀이를 보지 않고) 풀 수 있는지, 다르게 읽힐 곳이 없는지.
3. 다섯 문제가 정말 1 → 5로 어려워지는지, 앞 문제를 푼 사람이 다음 문제에서 "아, 그때 그거에 이게 붙었구나" 하게 되는지.
4. 실전 신호가 그 문제에만 통하는 말이 아니라, 다른 문제에서도 같은 표현을 보면 떠올릴 수 있는 말인지.
